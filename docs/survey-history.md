# Survey History (multi-survey persistence)

## What changed

Previously, each user's survey data was stored on their `user_sessions` row (one
per login). A second survey in the same login **overwrote** the first, so only the
latest assessment survived.

Now every completed survey is persisted as its own row in a dedicated
`survey_records` table, keyed by a per-survey `survey_run_id`. One login can own
many survey records, so the full assessment history is preserved.

## New table — `survey_records`

| Column | Notes |
|---|---|
| `survey_run_id` | PK — UUID generated by the frontend, one per survey run |
| `user_id` | FK → `users(user_id)` |
| `session_token` | login the run came from |
| `session_id` | frontend session id |
| `survey_type` | `TEST` / `BATFULL` / `CBTFULL` |
| `created_at`, `updated_at` | ISO timestamps |
| `survey_results` | JSON — per-question score + biometrics |
| `technical_report` | JSON — total score, risk level, domain totals |
| `prompt_info` | JSON — consultative response + `ssotReport` |

Index: `idx_survey_records_user (user_id, created_at DESC)`.

`user_sessions` now serves **auth only**; its survey columns are no longer written.

## End-to-end flow

```
Frontend                         Backend                         DB
--------                         -------                         --
new assessment → mint            /analyze-report  ──┐
survey_run_id (App.tsx)          /ssot-report     ──┼─ ensure_survey_record(run_id)
   │ passes run_id + type        (run_id keyed)     ├─ save_survey_record_results
   ▼                                                ├─ save_survey_record_snapshot (COALESCE)
DetailedReport sends             /api/history       └─ update_survey_record_ssot (merge)
survey_run_id + survey_type      → get_user_survey_records(user_id)
in both POST bodies                                   → survey_records (newest first)
```

All three writes for one run converge on the same `survey_run_id`, so the snapshot,
the full report, and the KB/SSoT result land on a single record. `ensure_survey_record`
is `INSERT OR IGNORE`, so whichever write fires first creates the row safely.

## Key files

| Layer | File | Change |
|---|---|---|
| DB schema | `app/backend/db_init.py` | `survey_records` table + index |
| DB access | `app/backend/db.py` | `ensure_survey_record`, `save_survey_record_results`, `save_survey_record_snapshot`, `update_survey_record_ssot`, `get_user_survey_records`; admin count now per survey |
| Endpoints | `ciq/reports/routes.py` (`/analyze-report`, `/ssot-report`), `ciq/api/history_routes.py` (`/api/history`) | keyed by `survey_run_id`; registered in `ciq/server.py` |
| State | `app/frontend/src/App.tsx` | `surveyRunId` state, regenerated per assessment |
| Report | `app/frontend/src/components/ui/detailed-report.tsx` | sends `survey_run_id` + `survey_type` |
| Types | `app/frontend/src/types.ts` | `UserSession` → `SurveyRecord` |
| History UI | `app/frontend/src/components/ui/user-history.tsx` | renders `records` |

## Notes

- The table is created automatically by `init_db()` on backend startup — no manual migration.
- Existing survey data in old `user_sessions` rows is **not** migrated (fresh start).
- `/api/history` response shape changed: `{ sessions: [...] }` → `{ records: [...] }`.
