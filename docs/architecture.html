CIQ — Architecture & Data Flow voice burnout assessment

A voice-driven burnout assessment app. A realtime voice agent administers the BAT survey while the browser captures facial biometrics; a multi-stage LLM pipeline then turns the answers + biometrics into a behavioral analysis and a spoken consultative report. This document maps every model in the system, exactly what data each one consumes, what it produces, and what you can ask it.

② End-to-End Flow Two phases: a live voice survey, then an on-demand report pipeline.

Key insight: the realtime voice agent (model ①) never sees the full report. It only receives per-question tool acknowledgements during the survey, and later a compact report_context string for Q&A. All heavy analysis happens in models ②–④ via separate HTTP calls after the survey ends.

④ The Biometric Pipeline Where every biometric value originates, and how it reaches a model.

Capture (browser)

  • Blink rate — MediaPipe eye-openness (EAR < 0.1 = blink), 30 s rolling window, EMA-smoothed. Baseline captured in a 30 s calibration session stored in localStorage.
  • Blink-rate change % — deviation of current blink rate from the personal baseline.
  • Gaze (x,y) — left-iris position vs. an adaptive baseline, amplified to a 0–1 signal.
  • Pupil size, head pose, smile — computed but used only for the live video panel.
  • Face emotion — separate loop sends JPEG to AWS Rekognition every 3 s.

Transport & capture-at-answer

  • POST /biometrics continuously updates SessionState: sentiment, blink-rate change, face emotion, gaze, and appends to rolling history buffers.
  • POST /analyze-stress → rule engine → POST /update-stress adapts agent tone in real time.
  • When the agent fires record_survey_response, _survey_tool() takes a snapshot: it uses the average blink-rate change from history + current gaze + voice sentiment + response latency, and stores it under that question_id.
  • Those snapshots are what later feed models ②–④.
Two different blink numbers: the live stress engine uses a personal-baseline % change with a ±30% threshold; the report's br_stress label is recomputed in analyze_report with the same ±30 cutoff (>30 = High, <-30 = Low). Gaze and emotion are stored raw — no rule engine.

⑤ What You Can Ask Each Model Practical capability map.

① Voice Agent — during & after survey

Conversational. After the report it enters report_delivered → qa_mode and can answer follow-ups using query_survey_results.

  • "What's my burnout score / risk level?"
  • "Which areas contributed most?" → contributing_domains
  • "Which questions showed high stress?" → stress_questions
  • "Give me a summary." → summary
  • "What does the app do / is this medical advice?" → meta-intent

②③ Analysis & Consultant — one-shot

Not interactive — invoked by /analyze-report. You shape them via the data you send.

  • "Correlate scores with blink-rate signals." (②)
  • "Flag contradictions: high score but relaxed signal." (②)
  • "Explain the score and give next steps, spoken." (③)
  • Bounded to provided rules + data — returns insufficient_evidence rather than guessing.

④ Mithra KB — evidence report

  • "Root cause & recommendations for {risk} driven by {top domains}."
  • Custom query_override from the test generator.
  • Answers grounded in uploaded burnout documents, with citations.

⑤ ⑥ Vision / Biometrics

  • Not queryable in language — they emit signals, not answers.
  • Rekognition: "what emotion is on this frame?"
  • Interpreter: "is this blink rate stressed/relaxed/normal?"

⑥ Known Data Gaps Data that is captured but never reaches a model — worth knowing before you trust an answer.

Gaze position is invisible to the conversational agent. It is sent to the behavioral-analysis model (②), but: (a) query_survey_results never returns gaze in any of its 5 query types, so the voice agent cannot answer gaze questions; and (b) the analysis prompt's research rules only describe blink rate, so model ② is grounded to ignore gaze and return insufficient_evidence. rtmt.py _query_survey_tool · app.py research_rules
Face emotion (Rekognition) is dropped before report generation. It is stored in face_emotion_history and a _get_dominant_emotion() helper exists, but it is never written into the per-question snapshot and never appears in input_data or any report prompt.
Response latency & verbatim answer text are stored in survey_results and sent to the frontend snapshot, but are excluded from the model-facing input_data and consultative prompt.
To make a biometric usable by a model you generally need two changes: (1) expose it through query_survey_results for the voice agent, and (2) add a matching research rule + include it in input_data for the analysis model.
